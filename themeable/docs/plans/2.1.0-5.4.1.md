# 2.1.0-5.4.1 Development Plan

*Theme settings for every user, theme permissions, and the move to IceRom*

Nov 14, 2026 · revised Nov 16, 2026 · Stealthx3 · **The user-side phases still need their detailed design; open decisions are listed below**

This release brings the features deferred from 1.1.0: each user can choose their own theme, RomM's permission groups decide who may change themes and manage packs, packs can be public or private, and theme changes are logged. Its last phase is housekeeping: romm-themeable becomes IceRom, a RomM fork built to host several feature modules, with themes as the first. The image published at the end is the first IceRom image.

## Phases A to D: the user-side overhaul

These are the features deferred from 1.1.0, as that plan listed them. Each phase starts with a design pass with the owner: illustrated options for the screens, like the Branding layout options of Oct 22, and the decisions above. The phase's detailed steps are then written into this plan before any code.

- **A. Permissions.** Choosing a theme for oneself, setting the server's theme, and managing packs (upload, rename, delete, restore built-ins) each become a permission in RomM's permission groups. Branding shows only what the user may do, and the backend refuses the rest whatever the page sends. Rename and delete rules follow from these permissions.
- **B. User Theme.** A section in each user's settings to choose a theme, Random included, or follow the server's. The choice is saved to the user's account, so it follows them across devices; it replaces the per-browser choice for signed-in users, and the per-browser choice remains for the login screen.
- **C. Public and private packs.** A pack uploaded by a user is private to them unless they make it public. An administrator who applies a private pack as the server's theme sees a warning first. Uploads by users who aren't administrators use the same checks and limits as Branding's.
- **D. Audit trail.** Every theme change (server theme, uploads, renames, deletions, visibility, permission-driven refusals) is recorded with who and when, and Branding shows the recent entries.

The original request and design for these are in the Docs plan "Themeable Development Plan: Archives, Random Theme, Uploads and Per-User Themes" (Oct 18).

## Phase E: housekeeping, IceRom

The final phase before the release is published. It changes no behaviour from phases A to D; it moves, renames and rebrands.

### E1. Layout for modules

`git mv` keeps each file's history (`git log --follow`).

```
icerom/
  package.json          product version and the npm scripts
  ROMM_VERSION
  GUIDELINES.md
  core/
    lib/                args, zip, source (overlay and patch engine), html, sw
    scripts/            apply-source, check-upstream (core half), failure-report, verify-deployment
    test/
  docker/               Dockerfile and entrypoint for the whole image
  docs/
    plans/              every release plan, 1.1.0 onwards
    decisions.md        the owner's decision and action log
    modules.md          how a module plugs in
    images/             landing-page screenshots and brand art
  modules/
    themeable/          the theme module: lib, loader, picker, packs, overlay, patches,
                        schema, catalog, scripts, test, dev, docs
```

**Module contract** (`icerom/docs/modules.md`). Each module has a `module.json` naming:

- its overlay and patch folders;
- its start-up step;
- the files it adds to the image;
- its checks: unit tests, source-check paths and any visual check.

`core/scripts/apply-source.mjs` applies every module in one pass and fails on two modules claiming the same file or anchor. The Dockerfile and entrypoint loop over the modules.

**Workflows** become `icerom.yml`, `icerom-upstream.yml`, `icerom-source.yml` and `icerom-themeable-visual.yml`, with their `paths` filters and docs-only exclusions moved along. `npm test` from `icerom/` runs every test.

### E4. Switch-over (owner checklist)

In this order, after E1 to E3 are pushed:

1. Rename the GitHub repository to `IceRom`; GitHub redirects old URLs and remotes. Set the description, topics and the social preview card.
2. Add `ICEROM_BOT_TOKEN` and, if used, `ICEROM_AUTO_MERGE`.
3. Close the desktop app's connection to the folder, run `mv /mnt/FileDrive/Personal/Projects/Git/romm-themeable /mnt/FileDrive/Personal/Projects/Git/IceRom` and `git remote set-url origin https://github.com/Stealthx3/IceRom.git`, then reconnect the folder.
4. Rename the Claude Project to IceRom and replace its guidelines copy.
5. After the first IceRom image is published, make `ghcr.io/stealthx3/icerom` public and link it to the repository.
6. Delete `THEMEABLE_BOT_TOKEN` and `THEMEABLE_AUTO_MERGE` once the new ones work; the fallback goes in the next release.

### E5. Verification and release

1. Unit, upstream, source and visual checks, and the preview recipe.
2. The lab runs a check for every instruction this release changes, on `main` and the release branch:
   - the user-side features;
   - the new compose file and image name;
   - the module layout;
   - manual adoption under `icerom/`;
   - the storage-key move.
3. **Upgrade check:** an install running `romm-themeable:2.0.5-5.4.1` switches its image to `ghcr.io/stealthx3/icerom:5.4.1`, keeping its database and themes volumes. It must keep its server theme, uploaded packs, Branding settings and users' choices.
4. With approval, merge into `main`, which builds, verifies and publishes the first IceRom image.
